# 以「腎超新」為主體，逐步吸收訓練引擎

> **後續決定（2026-10-29）**：本報告是研究當時的建議，內文不修改。專案之後的決定如下（編號見 [決策紀錄](../../決策紀錄.md)）：
> - 分割以系統內建的 ResNet34-UNet 為主，nnU-Net v2 當外部基準（不是以 nnU-Net 為主）。
> - 不沿用舊 UNet 當備援或預先標註工具；所有模型重新訓練（D1）。
> - MedSAM 只當選用的比較工具（D3（改））；遮罩改由醫師在系統外圈選後上傳（D16）。
> - 肝、脾由醫師圈影像中看得到的整個器官；同深度取樣由程式負責（D19），不另畫固定大小的參考區。
> - 不做影像品質與切面分類模型（D25）。
> - eGFR 擴充為 2／3／5 類，並比較影像、臨床、遮罩等輸入方式（D22、D23）。

**結論先講**：合併時以系統 B（桌面「腎超新」）為主體，把系統 A（ISU_AI_KUA）的訓練引擎拆成幾個模組，一次搬一個進 B。這是 strangler-fig 加 branch-by-abstraction 的做法，不做一次性重寫 ([Fowler, Strangler Fig](https://martinfowler.com/bliki/StranglerFigApplication.html); [Fowler, Branch by Abstraction](https://martinfowler.com/bliki/BranchByAbstraction.html))。搬遷期間 A 保持可執行、只讀，當作數值比對的基準（oracle）。B 已壞的 60 個模型與遮罩功能不修，直接由 A 的 UNet-512 路徑取代。模型方面的判斷如下：

- **分割**：UNet-512 只在過渡期沿用；新任務改用 nnU-Net 2D 多類別模型。
- **分類 backbone**：沿用 ResNet18 與 EfficientNet-B3，淘汰 MobileNetV2。
- **有序分級**：CORAL 要和 CORN、cross-entropy 一起比較，並加上 temperature scaling。
- **MLP-ResNet18**：改做回音 Grade 0–3 的 hybrid 主架構。
- **多張影像整合**：先用每側腎臟的校準機率平均，ABMIL 只當實驗。
- **影片與病灶**：影片關鍵影格和囊腫/結石/積水偵測都是新模組，排在合併穩定之後。
- **eGFR 五類**：降為輔助任務（例如 eGFR<60 二元或與分級做相關分析），不再當主要成果。

這個判斷的根據是：台灣 Kuo 2019 用了約 1,300 名病人，eGFR 迴歸也只有 r=0.741，二元 CKD AUC 0.904 ([PMC6550224](https://pmc.ncbi.nlm.nih.gov/articles/PMC6550224))。本專案只有約 181 名病人，切五類必然不穩。工具列建議改成「臨床／研究」兩個工作台，用角色控制誰看得到哪一邊，原本約 40 個導覽項目收斂成約 17 個去處。這棵導覽樹是**未經使用者測試的設計意見**。另外三點要先標明：本報告引用的韓國 hybrid 研究數字只來自摘要的搜尋摘要；目前**沒有任何已發表的 Grade 0–3 回音分級模型**；多數權重的授權仍待逐一查證。

## 1. 結論摘要

### 1.1 合併策略：B 當宿主，A 拆成可替換的模組

B 的功能比 A 完整：有三區架構、病人對應、受保護計算檔清單，所以由 B 當宿主。A 的價值在訓練引擎（CORAL、K-fold、停止/恢復、SSE、背景佇列）和唯一能用的 UNet-512。做法是在 B 裡為每個能力定義 port，例如 `DatasetPort`、`PreprocessPort`、`SegmenterPort`、`ClassifierTrainerPort`、`ModelRegistryPort`、`JobRunnerPort`，A 的程式碼就是這些 port 的第一個實作。Hexagonal 架構讓邏輯可以「由使用者、程式、自動化測試或批次腳本同樣驅動」 ([Cockburn](https://alistair.cockburn.us/hexagonal-architecture/))，所以 A 與 B 的數值比對可以寫成不需要 React UI 的腳本測試。

B 壞掉的 mask 函式剛好適合 branch by abstraction：先在呼叫端前面加一層抽象，接上 A 的 UNet-512，比對輸出後再刪除 B 的舊實作。Fowler 也指出，舊系統大部分行為本來就不值得重現 ([Fowler](https://martinfowler.com/bliki/StranglerFigApplication.html))，所以**不要嘗試修好那 60 個模型**。

架構上維持單一 FastAPI、單一 SQLite、一個模組一個 package 的 modular monolith。團隊只有 1–3 人、只用一台 Windows 機器，拆成微服務沒有好處。這一點是工程判斷，本次研究沒有引用 modular monolith 的專門文獻。

合併中最大的風險是**資料洩漏**，不是程式碼本身。舊切分是以影像為單位，而且檔名前綴就是 eGFR 標籤，所以 A 的舊成績和 B 的 59 個分類器成績都要視為不可比較，必須在病人層級切分上重跑。一份 kidney-stone CT 的預印本顯示，影像層級切分的 AUC 約 0.999，改成病人層級切分後降到 0.946 ([Research Square，未經同儕審查](https://www.researchsquare.com/article/rs-10604877/latest))。這個數字只用來說明洩漏的量級。

## 2. 合併計畫

### 2.1 九個階段，每個都有可量測的出口條件

階段的順序依照一個原則：先建立基準與防護，再搬確定性的計算，最後才搬訓練和新任務。A 在 Phase 0–4 期間都是 oracle。下表的容許誤差是建議起點，正式門檻應該用 Phase 0 量到的 A 自身 run-to-run 變異來定。PyTorch 官方明說，跨版本、跨平台、CPU 與 GPU 之間都**不保證完全可重現** ([PyTorch 2.6 Reproducibility](https://docs.pytorch.org/docs/2.6/notes/randomness.html))。

| 階段 | 目標 | 要搬／動的模組 | 主要風險 | 驗證方式／完成標準 |
|---|---|---|---|---|
| **0 凍結與基準** | 把 A 定為 oracle | 兩個 repo 打 git tag、複製兩份 `.db`；鎖定環境（torch 2.6、CUDA、numpy、opencv、skimage），A 與 B 用同一份 | 環境差異讓後面所有比對失真 | 約 50 張影像的 golden outputs（前處理圖、mask、特徵、分類機率）連同 SHA-256 一起 commit；同一設定跑 3 個 seed，記錄變異表；B 的 DB 完成 `alembic stamp` baseline |
| **1 資料層與防洩漏** | 所有影像對應到病人，標籤只來自表格 | `data` 模組：以 SHA-256 為 key 的冪等 ETL（`import_from_A.py`，含 dry-run 報表）；檔案改成不透明名稱；`splits` 表存 `patient_id → fold` | 檔名前綴的 eGFR 洩漏；同一病人跨 train/test；近似重複影像 | 975 張 = 匯入 + 去重略過；沒有 patient_id 的影像為 0；每次切分的病人交集 = ∅；「讀取 original_filename 即失敗」的測試通過；列出每個 fold 的類別數 |
| **2 合約與模型庫** | 每個模型都帶機器可檢查的 I/O 合約 | `registry`：manifest（input_contract、preprocess_spec_id、upstream_models、lineage、model card），格式參考 MONAI Bundle；B 的 60 個模型標成 `archived/broken`（先不刪） | UNet 512 和 1024 混用，系統默默 resize | 單元測試：把 1024 合約的 UNet 餵進 512 pipeline 時 `inference.load()` 必須 raise；此階段 champion 數量為 0 |
| **3 搬確定性計算** | 前處理 → UNet-512 mask → 特徵 | `preprocess`、`segmentation`、`features` 放到 `SegmenterPort` 等 port 後面；刪除 B 的壞 mask 函式；加入受保護計算檔清單 | skimage/OpenCV 版本差造成特徵漂移 | 前處理 byte-identical；mask Dice ≥ 0.999；Length_px 完全一致；GLCM entropy 與對比度的相對誤差約 1e-6；分類機率誤差約 1e-5 且 argmax 一致 |
| **4 搬訓練引擎** | CORAL、四個 backbone、K-fold、resume、佇列、SSE | `training` + `JobRunnerPort`（先保留 A 的佇列）；GPU 訓練在獨立 process 跑；SSE 從 SQLite 進度表輪詢 | resume 沒存 RNG/optimizer 狀態；CUDA OOM 讓 API 掛掉 | 用 A 的舊影像層級 folds（僅供這次對等測試）重現每個 fold 的指標，落在 Phase 0 變異帶內；停在第 k 個 epoch 再 resume，結果和不中斷的 run 落在同一帶內；kill worker 後 API 仍存活；第二個 GPU 工作會排隊 |
| **5 病人層級重建基準** | 舊成績降級為「洩漏、僅供參考」 | `evaluation`：在病人層級 folds 上重訓，報告病人層級指標與信賴區間 | 稀有類別的 fold 病人數極少 | 評估報告可由 registry 產生；每個 champion 都有完整 lineage（split hash、data hash、受保護檔 hash） |
| **6 接上臨床區** | 臨床只用 champion | `clinical` 只依賴 `inference` 和 `registry`；PDF 報告寫入 model_id 與版本，並加註研究用途 | 臨床程式誤引用訓練程式 | 端到端測試：從儀器收圖到產出帶版本號的 PDF；import-linter 規則禁止 `clinical` 匯入 `training` |
| **7 退役與清理** | A 封存，移除過渡層 | A 改為唯讀；B 的壞模型在**人工簽核後**才永久刪除 | 太早刪掉參照資料 | 除了封存的 golden 檔以外，所有測試都不需要 A；受保護計算回歸測試全綠 |
| **8 新方向** | Grade 0–3、病人整合、影片、病灶 | 新的 `task` enum 值，加上 `video_ingest`、`detection`、`patient_aggregation` 模組 | 影片影格是不同的資料分布 | 每個任務都有自己的合約和病人層級評估 |

### 2.2 階段背後的幾個技術決定

**資料庫遷移**：Alembic 在 SQLite 上要用 `render_as_batch=True`，因為 SQLite 的 ALTER 很有限，batch 模式會重建資料表再複製資料。約束一定要命名，否則未命名的 FK 和 CHECK 在重建時會遺失 ([Alembic batch](https://alembic.sqlalchemy.org/en/latest/batch.html))。A 的資料用 ETL 匯入，**不要直接合併 DB 檔**。

**工作佇列**：Celery 自 4.x 起官方不支援 Windows ([Celery FAQ](https://docs.celeryq.dev/en/stable/faq.html))。FastAPI `BackgroundTasks` 和 API 在同一個 process 裡，只適合小任務 ([FastAPI](https://fastapi.tiangolo.com/tutorial/background-tasks/))。實際可行的是保留 A 的佇列，或改用以 SQLite 為後端的 Huey ([Huey docs](https://huey.readthedocs.io/en/latest/))。⚠ **兩者沒有共識**：Huey 多了重試和排程，A 的佇列則已經和 checkpoint 的停止/恢復綁在一起。建議先放在 `JobRunnerPort` 後面，之後再決定。

**切分與洩漏**：用 scikit-learn `StratifiedGroupKFold(groups=patient_id)`。它保證每個 group 只出現在一個 test fold，但分層只是盡力而為，大 group 多時會退化成接近 GroupKFold ([scikit-learn](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.StratifiedGroupKFold.html))。Varoquaux & Cheplygina 的建議是：一開始就切出 test set，而且要在任何資料轉換之前；超參數選擇不能碰 test；test set 要附信賴區間 ([PMC9005663](https://pmc.ncbi.nlm.nih.gov/articles/PMC9005663))。Kapoor & Narayanan 在 17 個領域、294 篇論文中找到洩漏問題 ([PMC10499856](https://pmc.ncbi.nlm.nih.gov/articles/PMC10499856))。

SHA-256 只能抓到完全相同的檔案。同一影格的不同 JFIF 壓縮、或影片中連續的影格，需要 perceptual hash 才抓得到，而且至少要確保它們都留在同一個病人 group 內。這一點在 Phase 8 影片工作時會變得關鍵。

**模型合約**：MONAI Bundle 的 `network_data_format` 定義了 `spatial_shape`、`dtype`、`value_range`、`channel_def` 等欄位，MONAI Label 會在推論時直接讀取這些欄位 ([MONAI Bundle spec](https://monai.readthedocs.io/en/latest/mb_specification.html); [MONAI Label source](https://docs.monai.io/projects/label/en/stable/_modules/monailabel/tasks/infer/bundle.html))。MLflow 的 alias 概念（例如 `champion`）適合拿來描述臨床「上線版本」 ([MLflow Model Registry](https://mlflow.org/docs/latest/ml/model-registry/))。不過本機用 SQLite 表自己做就夠了，MLflow 在 Windows 上完全離線運作的情況本次未驗證。

## 3. 模型評估表

以下各表的「資料需求」和「運算需求」，除非附上來源，都是研究筆記的推論。授權欄標 ⚠ 的項目必須在採用前打開官方 repo 的 LICENSE 檔確認。

### 3.1 分割：整腎已解決，皮質與腎竇才是難點

文獻中整腎超音波分割的 Dice 大多在 0.90–0.97：YSegNet 700 張 97%、Fast-UNet++ 三中心 744 張 >95%、多尺度 CNN 7,350 張 95.86% ([Frontiers review PMC12832298](https://pmc.ncbi.nlm.nih.gov/articles/PMC12832298/))。內部結構難很多。在 OKUD 上，MAT-UNet 的 capsule 為 93.83%、central echo complex（≈ 腎竇）84.34%，medulla 只有 66.34%、cortex 58.93% ([MDPI Diagnostics 2025](https://www.mdpi.com/2075-4418/15/15/1978/htm)，⚠ 全文 403，數字來自搜尋片段)。

所以「cortex = 腎 − 腎竇」比直接切 cortex/medulla 更可行：直接分割腎竇，再用相減得到實質。同一篇 review 也提醒，不同操作者會讓 Dice 差 5–7%，成人模型用在兒童資料上表現約下降 22% ([PMC12832298](https://pmc.ncbi.nlm.nih.gov/articles/PMC12832298/))。

point prompt 在超音波的弱邊界上表現會變差，所以標註時用 box prompt ([SAMUSA, MICCAI 2025](https://papers.miccai.org/miccai-2025/paper/3015_paper.pdf))。肝/脾的回音參考**不要用整個器官的 mask**，而是在與腎皮質 ROI 同深度的實質放固定大小 ROI，避開血管、包膜和聲影。這個做法有 Fast-Unet 肝腎指數的先例（腎 Dice 94%、肝 97%，[ESR 會議摘要](https://connect.myesr.org/?p=42230)），也和 Cha 2021 自動 HRI 研究一致：肝、腎量測與放射科醫師的 ICC 約 0.92，HRI 約 0.73 ([PMC8446496](https://pmc.ncbi.nlm.nih.gov/articles/PMC8446496))。Philips 有一件自動 HRI 專利 US 12026886 ([Google Patents](https://patents.google.com/patent/US12026886))，做產品時要留意智財風險。

**結論**：UNet-512 **沿用**到 nnU-Net 在同一個病人層級 test set 上贏過它為止，之後退為預標註器。fine-tune 現有 UNet 改成 5 類雖然可行，但它缺少 nnU-Net 的 augmentation、deep supervision 和 CV，花的力氣和直接換掉差不多。

### 3.3 回音 Grade 0–3：沒有已發表模型，hybrid 是最站得住的架構

⚠ **本次研究沒有找到任何已發表的深度學習模型，能輸出醫師定義的四級（Grade 0–3）腎皮質回音分級並附每級機率**，所以這是一個新目標，沒有共識 benchmark。

先前的入門研究也確認了三件事。第一，團隊的四級分法對應到文獻中歸給 Hricak 1982 的分級（取自二手來源）。第二，**沒有公開的灰階比值 cut-off 可以對應 Grade 0–3**；1.0 與 1.15 只是單一研究的「異常」閾值，不是分級邊界 ([DOAJ, Kidney Blood Press Res 2017](https://doaj.org/article/da03193e070c494689d7fbbb8ed876df))。第三，**找不到目測分級的醫師間 kappa 研究**。標註雜訊的上限，必須由團隊自己量測。

可以直接支持 hybrid 設計的證據有幾項：

- kidney/liver 平均像素密度比值在 197 名病人中與追蹤 eGFR 呈負相關（r=−0.684）([DOAJ](https://doaj.org/article/da03193e070c494689d7fbbb8ed876df))。
- 電腦計算的 renal/liver 比值預測 IFTA>50% 的 AUC 為 0.83，合併其他發現後達 0.95 ([GMSMJ](https://he02.tci-thaijo.org/index.php/gmsmj/article/view/262871))。
- 韓國 Severance 研究（909 名病人）用 Mask R-CNN 抽出腎長與腎/肝回音比，加進 ResNet18 後 AUROC 從 0.81 升到約 0.88，再加糖尿病約 0.91 ([Yonsei repository](https://ir.ymlib.yonsei.ac.kr/handle/22282913/193103))。⚠ **這組數字只來自搜尋引擎對摘要的摘要，repository 頁面直接抓取失敗，期刊與 DOI 也未驗證。引用時要標明，並在寫論文前取得原文。**

| 候選 | 文獻出處 | 資料需求 | 運算需求 | 授權 | 建議 |
|---|---|---|---|---|---|
| 透明 baseline：分割 → 同深度 cortex/liver(spleen) 比值 ＋ 紋理統計 → ordinal logistic regression | 上述比值研究 | 分割 mask ＋ 分級標籤；cut-off 要在院內學 | CPU | 自寫／scikit-learn | **新增，當作 CNN 必須超越的下限** |
| MLP-ResNet18（影像 ＋ 臨床 ＋ 自動量測比值、腎長） | 和韓國 hybrid 同構 ⚠ | 同上 | 單 GPU 訓練、CPU 推論 | 自有 | **沿用並改用途（主力）** |
| 輸出頭：CE＋softmax | 直接給出 P(Grade 0..3)，最容易校準 | — | — | — | 保留為 baseline |
| 輸出頭：CORAL | 現有；CORN 論文中在 MORPH-2/AFAD 明顯輸給 OR-NN ([arXiv 2111.08851](https://arxiv.org/pdf/2111.08851)) | — | — | `coral-pytorch`（⚠ 授權待查） | **微調／比較** |
| 輸出頭：CORN | 以條件訓練子集 ＋ chain rule 保證 rank consistency，原作者 benchmark 表現不輸 CORAL ([arXiv 2111.08851](https://arxiv.org/abs/2111.08851v5)) | — | 同 CORAL | 同一套件 | **加入比較** |
| 校準：temperature scaling | Guo 2017 ([arXiv 1706.04599](https://arxiv.org/abs/1706.04599)，經典文獻，本次未重新抓取) | 用 out-of-fold 預測擬合 T（要 nested，避免洩漏） | 可忽略 | — | **新增**；報告 ECE 與 reliability diagram |

三種輸出頭（CE、CORAL、CORN）用同一組病人層級 folds 跑，報告 accuracy、MAE、quadratic weighted kappa、ECE 與各級 recall。CORAL/CORN 的 temperature scaling 要套在 K−1 個二元 logit 上，共用一個 T。每級機率等於相鄰累積機率的差。Grade 3 很可能是稀有類別，要用 class weight 或平衡抽樣，而且不能在影像層級跨病人 oversample。

比值會受到 gain、深度、TGC、機型影響，所以機型和 preset 要記錄下來當作共變數。脂肪肝會讓腎相對變暗、低估分級，這種情況應改用脾比較，或把影像標為「參考器官異常」。這兩點延續先前入門報告的陷阱表。

### 3.4 多張影像 → 病人層級：先做簡單、可校準的整合

| 候選 | 文獻出處 | 資料需求 | 運算需求 | 授權 | 建議 |
|---|---|---|---|---|---|
| 單張挑選（最長腎長影像） | Kuo 2019 測試時每個 study 只取最長腎長那張 ([PMC6550224](https://pmc.ncbi.nlm.nih.gov/articles/PMC6550224)) | 需要腎長 | 極低 | — | 當對照組 |

| 多數決 | — | — | — | — | 不採用（丟掉機率資訊） |

不推薦一開始就用 ABMIL，有兩個證據。第一，主動脈瓣狹窄的多視角心超研究發現，標準 attention MIL 會把注意力放在不相關的影像上，需要用監督式 attention 修正 ([arXiv 2306.00003](https://arxiv.org/html/2306.00003v3))。第二，MICCAI 2025 在超音波上發現 attention aggregator 的鑑別力較好，但**校準較差、較過度自信**，instance-level 方法給出的風險估計反而較可靠 ([MICCAI 2025 #4101](https://papers.miccai.org/miccai-2025/paper/4101_paper.pdf))。只有約 181 個 bag 時，這兩個問題都會被放大。

另一個結構性問題是：回音分級是**以單側腎為單位**（右腎對肝、左腎對脾），兩側可以不同。所以要先在每一側內整合，再決定病人層級要報「取較高等級」還是兩側分開列出。這需要醫師決定。⚠ 目前沒有找到腎臟超音波 CKD 或回音分級的 MIL 研究。

### 3.5 影片關鍵影格：品質分類 ＋ 量腎長，選最長長軸

最接近的研究是 Seraj et al.（Sci Rep 2025）。他們用 211 名病人的 1,203 個影格標成 Good/Bad/Null，YOLO11x-cls 最佳，5-fold 病人層級 CV 平均準確率 90% ± 5.9%。但這篇**沒有長軸條件，也沒有說明在多個 Good 影格中如何選一張**，而且內文和表格的 F1 數字彼此不一致 ([PMC12647705](https://pmc.ncbi.nlm.nih.gov/articles/PMC12647705))。胎兒 SonoNet 在儲存的影片中檢索標準切面的準確率是 90.09% ([arXiv 1612.05601](https://arxiv.org/pdf/1612.05601))，可以參考它的方法。

| 候選 | 文獻出處 | 資料需求 | 運算需求 | 授權 | 建議 |
|---|---|---|---|---|---|
| YOLO11x-cls 品質分類 | Seraj 2025 | 約 1.2k 個標註影格 | GPU 較佳 | **AGPL-3.0**，商用或封閉產品需要 Enterprise 授權 ([Ultralytics](https://ultralytics.com/license)) | 不採用（授權） |
| ResNet18/MobileNet 品質＋切面分類器（Good 長軸／其他切面／無腎） | 推論；Seraj 證明此規模可行 | 推估約 1k 個院內影格 | CPU 可行 | torchvision BSD | **新增** |
| 分割 → 長軸長度 → 取 top-k（k=5–8）＋ 時間軸 NMS | 延伸 Kuo 2019 的最長腎長規則 | 依賴 3.1 的分割 | 低 | — | **新增**（需在院內自建，無現成方法） |

建議流程是：影片先降到 2–5 fps，經過品質/切面分類，對 Good 影格做分割、量長軸，取前 k 張交給 3.4 的整合器。時間軸 NMS 是為了避免連續近似影格灌票。從影片抽出的影格和醫師存下來的靜態圖分布不同（有動態模糊、gain 沒凍結），**分級器在影片影格上必須重新驗證**。

### 3.6 囊腫、結石、積水：文獻零散，排在最後

| 任務 | 候選與文獻 | 資料需求 | 授權 | 建議 |
|---|---|---|---|---|
| 積水 | 影像/腎層級分類或分級。台灣研究 3,462 個影格（97 名積水病人 ＋ 265 名對照），Res-UNet 對中重度積水準確率 94.6% ([NTU](https://scholars.lib.ntu.edu.tw/signposting/describedby/5a4de7c8-4f8e-4b81-b034-92d55be488fe)，⚠ 細節來自搜尋摘要)；兒童研究用積水面積/實質比值（HARP，168 名病人）([DOAJ](https://doaj.org/article/c9dce30c0180466cb814415804e833b1)) | 需要分級標籤（SFU 或醫師量表） | 沿用 BSD backbone | **新增**：沿用分類 backbone，或從腎竇/集尿系統 mask 的面積比推導 |

有幾篇公開資料集上的準確率高得可疑，例如積水 99.8% ([PMC11636695](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC11636695/))，review 已經點名過。另外，常見的 12,446 張「腎結石/囊腫」資料集其實是 **CT** ([DOAJ](https://doaj.org/article/c3c13ffafa0a4632a0553940cd8933ba))，找預訓練資料時要避免混入不同模態。⚠ 本次沒有找到可驗證、同時標有囊腫/結石/積水 bounding box 的公開腎臟超音波資料集。RTMDet 的授權有搜尋結果說是 GPL-3.0，但它發布在 MMDetection（通常為 Apache-2.0），**兩者矛盾，未驗證**。

### 3.7 eGFR 五類：降為輔助

Kuo 2019 用 4,505 張影像、約 1,300 名病人，eGFR 迴歸只有 r=0.741、MAE 17.6。二元 eGFR<60 的 AUC 0.904，但敏感度只有約 60.7%；切點改為 45 時 AUC 降到 0.83 ([PMC6550224](https://pmc.ncbi.nlm.nih.gov/articles/PMC6550224))。本專案的病人數約是它的 1/7，而且 <15 和 15–29 這兩類的病人可能各只有個位數，五類的每類指標會在 fold 之間大幅跳動。

eGFR 是全身性的檢驗值，B-mode 形態只能部分反映它。回音分級則直接定義在影像上，是更適合當主任務的視覺目標。建議 eGFR 保留三種用途：

1. **二元次要終點**：eGFR<60 或 <45。
2. **與分級的相關分析**：預測的 Grade 和 eGFR 做相關。
3. **多任務輔助頭**：選配。

五類頭停用，除非資料擴充到數百名以上病人，且每期都有足夠人數。就算只做輔助，也必須先在 Phase 5 用病人層級切分重跑。

## 4. 工具列設計稿

### 4.1 設計依據：把流程放進容器裡，而不是排在側欄上

成熟的 ML 工具用「容器」組織頂層導覽：ClearML 側欄約 6 個模組（Projects、Datasets、Pipelines、Model Endpoints、Orchestration、Apps），pipeline 的步驟在點進去之後才看得到 ([ClearML](https://clear.ml/docs/latest/docs/webapp/webapp_overview/))。MLflow 的訓練監控是 run 詳細頁的一部分，不是獨立頁面 ([MLflow Tracking](https://mlflow.org/docs/latest/ml/tracking/))。臨床影像工具則是「工作清單 → 病例 mode → 報告」：OHIF 的 Study List 是首頁，mode 是「為特定任務設定好的 viewer」，從清單啟動 ([OHIF Modes](https://docs.ohif.org/platform/modes/))。

臨床整合方面有一個直接的證據。JAMIA 2024 研究發現，AI 在 PACS 背景執行、結果直接出現在原本的影像序列中時，幾乎不干擾流程；舊式 CAD 需要另外開程式，「很多放射科醫師覺得麻煩而經常略過」 ([Farič et al., JAMIA 2024](https://pmc.ncbi.nlm.nih.gov/articles/PMC10746311/))。所以臨床端每多一個點擊，就多一分 AI 被略過的機會。

數量方面，Microsoft Fluent 建議左側導覽放 5–10 個同等重要的頂層類別，用群組標題分組，Settings 放頁尾，並明說「兩層是理想」 ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/design/controls/navigationview))。NN/g 認為頂層超過 7–9 項也可以，前提是有安排優先順序 ([NN/g](https://www.nngroup.com/articles/vertical-nav/))。跨多次操作的長流程，GOV.UK 建議用任務清單（task list）加少量狀態，而不是一步一頁 ([GOV.UK](https://design-system.service.gov.uk/patterns/complete-multiple-tasks/))。

自動化偏誤的證據要求 AI 輸出放在次要、可審查的位置。在 Dratsch 2023 的研究中，錯誤的「AI」BI-RADS 建議讓經驗不足讀者的準確率從約 80% 掉到 <20%，資深讀者（>15 年）從 82% 掉到 45.5% ([RSNA news](https://www.rsna.org/news/2023/may/ai-bias-may-impair-accuracy))。另一項 paired-reader 研究中，加上 AI 信心分數並沒有比只給文字結果更好 ([Radiology: AI ryai.220079](https://pubs.rsna.org/doi/epdf/10.1148/ryai.220079)，⚠ 全文 403，數字取自搜尋片段)。

⚠ **沒有找到任何同儕審查研究，直接比較「分區」和「角色可見性」兩種臨床導覽。** 以下樹狀結構是根據上述原則推出來的意見，**未做過 card sorting 或 tree testing**。

### 4.3 每項用途與設計理由

| 項目 | 用途 | 設計理由 |
|---|---|---|
| 工作台切換 ＋ 角色可見性 | 臨床和研究工具分開，研究人員兩邊都看得到 | 臨床路徑要短、不能夾雜研究工具（Farič 2024）；研究人員需要看到臨床輸出才能做回饋 |
| 工作清單 → 檢查工作區 | 一個病例的所有步驟集中在一頁 | OHIF「清單 → mode」模式；8 個步驟用 GOV.UK 式狀態清單，不放 8 個側欄項目 |
| 狀態清單的狀態 | 接收中 → 處理中 → AI 完成 → 草稿 → 已簽核 | 狀態數保持少量（GOV.UK 建議） |
| 模型說明抽屜 | 顯示目前上線模型的用途、指標、已知失誤 | 病理醫師希望先拿到 AI 的整體資訊，再看單一病例的輸出 ([Cai et al. "Hello AI"](https://www.researchgate.net/profile/Lauren_Wilcox2/publication/337135587_Hello_AI_Uncovering_the_Onboarding_Needs_of_Medical_Practitioners_for_Human-AI_Collaborative_Decision-Making/links/5e1ac19ba6fdcc28376bb0be/Hello-AI-Uncovering-the-Onboarding-Needs-of-Medical-Practitioners-for-Human-AI-Collaborative-Decision-Making.pdf)) |
| 報告編輯 | AI 預填欄位標成「AI 建議」，醫師確認後簽核；每個修改都記錄 | AI 預填結構化報告較快、品質評分較高 ([ESR AI blog, Jorg 2024](https://www.myesr.org/ai-blog/novel-reporting-workflow-for-automated-integration-of-ai-results-into-structured-radiology-reports/))；類別與證據（overlay、比值）放顯眼處，原始機率收在「詳細」裡 |
| AI 面板預設收合（選配） | 讓醫師先形成自己的判斷 | 降低自動化偏誤（Dratsch 2023）；⚠ 這是設計假說，沒有測試過 |
| 資料集（含 Splits 分頁） | 讓病人對應與切分看得見、可稽核 | 防洩漏是合併的核心（第 2 節） |
| 標註與回饋 | 醫師修正（mask／分級／病灶的差異）進入佇列，變成標註任務 | 對應 MONAI Label、CVAT 的 project → task → job 迴圈 ([CVAT](https://docs.cvat.ai/docs/workspace/)) |
| 流程執行 ＋ 單步工具 | 一般情況用一鍵 pipeline，進階使用者用單步工具 | ClearML「Pipelines → runs → step」 |
| 訓練（內含監控） | 刪掉重複的「訓練監控」頁 | MLflow／ClearML：監控屬於 run 詳細頁 |
| 模型庫（含「臨床上線」階段） | 取代原「模型中心」和「醫師分析方案」 | 對應 MLflow alias（champion）；臨床端只透過 alias 取模型 |
| 單一回收桶、單一設定、單一任務紀錄 | 三個回收桶、多份紀錄合併 | Fluent 把 Settings 和次要項放在頁尾；「合併」本身是推論 |
| 舊路由轉址 | 舊網址自動導向新頁 | ClearML 把 Datasets 搬位置後，使用者以為資料不見了 ([ClearML FAQ](https://faq.clear.ml/question/1523706241937838080/hi-i-ve-been-using-your-saas-platform-for-over-a-month-now-but-today-i-suddenly-noticed-most-of-my-data-is-missing-i-see-that-i-have-40-tasks-in-my-data-project-from-the-dashboard-as-it-should-be-but-inside-the-project-i-can-only-see-6-i-couldn-t-fin?desc=false)) |

## 5. 待確認問題

### 5.1 給指導教授：範圍與研究定位

1. **主任務改成回音 Grade 0–3，eGFR 降為輔助**，是否同意？論文或計畫書的主要終點要怎麼寫？
2. 舊的影像層級 eGFR 成績（A 與 B 的 59 個分類器）在 Phase 5 重跑後很可能明顯下降。是否接受把舊數字標成「洩漏、僅供參考」，並在報告中並列呈現？
3. 系統最後是學術原型，還是會交給醫院長期使用或商業化？這個答案決定 Ultralytics AGPL、OKUD 的 CC BY-NC-SA，以及 RadImageNet、USFM、UltraSam 權重能不能用。
4. 工作佇列要保留 A 的自製佇列，還是改用 Huey？模型庫要自建 SQLite 表，還是用 MLflow？（兩者都沒有共識。）
5. B 的 60 個舊模型，誰有權簽核永久刪除？什麼時候可以刪？
6. 容許誤差（Phase 3–4 的 Dice、特徵、指標帶）同意由 Phase 0 量到的 A run-to-run 變異來決定嗎？
7. 新方向的優先順序：病人層級整合 → 影片 → 病灶，這個順序可以嗎？
8. 是否預留時間做導覽的 tree testing（每個角色 5–8 人）？

### 5.2 給醫師：標註定義與臨床流程

1. Grade 3 是「**接近**」還是「**等於**」renal sinus？Grade 1（與肝同回音）在成人算正常嗎？二元切點用 ≥1 還是 ≥2？
2. 病人層級要報「兩側中較高的等級」，還是左右腎分開列？
3. 遇到脂肪肝、肝硬化、脾腫大時，要改用另一側參考器官，還是標成「無法分級」？
4. 是否願意參與醫師間與醫師自我重讀的 weighted kappa 測試？用 linear 還是 quadratic 權重？可以接受的門檻是多少？（文獻沒有基準。）
5. 分割標註要切哪些類別（實質、腎竇、肝 ROI、脾 ROI）？由誰標？每張可以花多少時間？（文獻中資深醫師每張 10–15 分鐘。）
6. 影片的「最長長軸影格」由系統自動挑選就可以，還是醫師要能改選？
7. 積水要用哪一個分級量表（SFU 或院內量表）？囊腫和結石要做到「有／無」、位置，還是大小？
8. 報告中 AI 結果的呈現方式：只顯示等級加證據 overlay，還是也要顯示各級機率？AI 面板要不要預設收合，讓醫師先自己判讀？
9. 報告簽核後，修改紀錄是否同意自動回流成研究用的標註資料？需要 IRB 涵蓋嗎？
10. 檢查工作區的 8 個步驟順序，是否符合實際門診或檢查室的流程？

## 結論

這次合併真正的分界線，不在 A 和 B 兩套程式碼之間，而在「洩漏前的成績」和「病人層級的成績」之間。只要 Phase 1 的病人切分和檔名防護完成，A 的訓練引擎和 B 的平台誰搬誰都只是工程問題。反過來，如果跳過這一步，再漂亮的整合也只是把不可信的數字搬到新介面上。所以 Phase 5 的「重建基準」不是收尾工作，而是整個合併最有研究價值的產出，也很可能讓舊的 eGFR 成績明顯縮水。教授要提早知道這件事。

第二個值得注意的是，新方向的每個模型其實都依賴同一個元件：一個能分出腎實質、腎竇、肝、脾的分割模型。回音比值、腎長、ROI 裁切、影片選格、積水面積比都從它衍生。換句話說，nnU-Net 多類別分割加上一份有 kappa 背書的 Grade 0–3 標註規範，是整個藍圖的關鍵路徑；backbone 的選擇反而是次要的。因為目前沒有已發表的 Grade 0–3 模型，也沒有目測分級的一致性數據，團隊把「共識標註、一致性量測、透明的比值 baseline」做紮實，本身就可能構成可以發表的貢獻。
