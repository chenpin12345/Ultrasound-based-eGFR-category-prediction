# 2026-10-13 改版：接收位址、醫師端預設方案、傳送端案例資料與清理

本文件是本次改版的現行說明。三區架構、本機模式、不可變方案／分析 run／報告等既有規則不變，仍以 [架構、API 與回復手冊](三區改版_架構_API與回復手冊.md) 為準。驗收證據在 `驗證報告/20261013-transfer-cases/`。

**界線**：同機 HTTPS 測試不等於兩台實體 Windows 驗收；沒有實際超音波設備、CUDA 或臨床適用性驗證。自動分析不等於醫師判讀，也不會自動確認報告。

## 2. 修改內容與架構理由

### 2.1 接收位址（只指 B 的監聽網卡）

三種位址分開：**B 的監聽位址**（本頁設定）、**A 連線的接收端位址**（由 B 產生的配對檔提供，含憑證與指紋）、**超音波設備位址**（本系統沒有網路設備協定，設備請用 USB／UVC 擷取）。

- B「真實圖片雙機示範」頁：自動偵測列出網卡名稱、IP、連線狀態與類型；127.0.0.1 標示「僅限本機測試」，169.254 標示其自動位址性質（不視為錯誤、也不優先）；只有一張已連線的區網卡時才自動選取，多張時要求使用者選擇。
- 手動輸入：後端 `network.validate()` 逐項說明原因：格式錯誤、IPv6（本版不支援）、0.0.0.0（會在所有網卡開放）、非私有網段、**不屬於 B 的網卡（例如誤填 A 或其他裝置的 IP）**、網卡未連線、連接埠超出 1024–65535。最後以實際綁定確認；埠被占用回報 `PORT_IN_USE`（接收程序改用獨佔綁定，不會與其他程式共用埠）。
- 記住上次成功設定（`receiver_settings`），每次開啟與啟動都重新驗證，失效時顯示原因，不自動換網卡。
- A 端不提供手動修改接收網址：憑證只綁定 B 當時的 IP，改網址只會導致驗證失敗。B 變更位址或重新開始接收時會重新產生憑證與配對檔，A 匯入新配對檔即可。
- 主應用仍只接受 loopback；區網只開放獨立接收程序的 `/pair`、`/batches`、`/items`、`/control`。

### 2.2 醫師端預設分析方案（模型區管理）

- 新表 `clinical_default_plans`（只能新增、不可修改或刪除）：每筆指定來源（`network_demo` 圖片傳輸／`capture` 設備擷取）、模式（指定方案／僅預覽）、不可變方案 ID、**相容依據**、設定者與時間。目前值＝該來源最新一筆。
- 設定時檢查：方案存在、封存權重與 manifest 雜湊一致、來源前處理不是「未確認」、有來源尺寸；設備擷取另需「已核實病人擷取適用性」。不讀研究區預設模型，不自動選最新或清單第一個。
- 方案需要哪些案例欄位由不可變方案快照決定（MLP → 年齡、糖尿病狀態），供 A、B 與待補資料判斷共用。
- 接收會話 API 必須明確指定 `analysis`：`{mode:'default'}`、`{mode:'preview_only'}` 或 `{mode:'plan', plan_id}`；省略或舊的 `plan_id` 欄位一律 422，不猜測。建立時解析並鎖定到 `demo_sessions`（`plan_id`、`plan_mode`、`default_setting_id`、`protocol`，資料庫觸發器禁止事後修改）。恢復會話沿用原鎖定；模型區之後變更預設只影響新會話。
- 預設無效或未設定時拒絕開始並說明原因，不會靜默改成僅預覽或換方案；「僅接收及預覽」必須明確選擇。
- 歷史結果顯示 run 實際使用的方案名稱與封存時間（影像結果、案例頁、報告分析版本選單），不以目前預設冒充。舊資料不追溯改寫。

### 2.3 傳輸協定 2 與案例資料

- 配對檔加入 `protocol:2`、`case_schema:1`、方案名稱與必填欄位（不含病人資料）。
- 批次清單每張圖片各自帶案例資料與其摘要：`{id, sha256, case, case_sha256}`。案例 schema 1 允許欄位：案例識別（必填）、病人識別、姓名、年齡（0–130 整數）、糖尿病（有／無／**未知**，未填≠無）、側別、檢查名稱、檢查時間（ISO 8601）、備註（≤500 字）；嚴格型別、未知欄位拒絕、整份 ≤4 KB。B 重算摘要，不符即拒絕。
- 冪等：同一項目重送，影像與案例摘要都相同才視為重試；不同則 409，不覆寫。
- 原子發布：先標記 `receiving` 並預配影像 ID → 寫入原始位元組（不轉檔、不縮圖）→ 單一交易建立示範案例、影像、案例資料版本 1 並更新項目。中斷時 `recover()` 只刪除該未發布的精確暫存目錄並回到 `pending`，不會留下可分析但資料配錯的案例。
- 示範資料域不變：一律 `kind='demo'`、`patient_id=NULL`；傳入的姓名與病人識別只是示範顯示欄位，標示「未核實」，不能操作正式病人。正式病人網路匯入仍未開放（需另行設計授權與身分關聯）。
- 病人資料只存在醫師資料庫；不寫入 URL、配對檔、錯誤訊息或日誌。A 工具只放在記憶體，A 的狀態表以案例識別呈現，AI 結果只在 B。
- 舊版工具（協定 1）上傳清單時收到 `426 SENDER_UPGRADE_REQUIRED` 與升級說明；新版工具匯入舊版配對檔時也會拒絕並說明。

### 2.4 案例資料版本與自動分析狀態機

```
pending → receiving → received_only（明確僅預覽）
                    → needs_data（缺方案必填欄位，列出缺項）
                    → queued → analyzing → completed／unavailable／failed
needs_data ──補齊資料（只成功一次）──→ queued
analyzing ──運算資源忙碌──→ waiting（批次暫停，可按繼續）
pending／queued／waiting／needs_data → cancelled
```

- 新表 `exam_basic_versions`（只增不改）記錄每個案例資料版本；既有案例以目前內容回填為 `legacy` 版本，不虛構更早歷史。B 端修改使用 `PUT /api/clinical/exams/{id}/case?expected_revision=`，版本衝突 409。
- 待補資料不占推論佇列（佇列上限 2，只計本會話的等待／分析中項目），但其影像仍計入 2 GB 暫存上限；結束會話時未保存影像照舊清理。
- 補齊資料後以條件更新 `needs_data→queued` 保證只排程一次；仍缺資料則更新缺項。舊分析 run 與已確認報告保持原本的資料快照。
- 不帶入 0、空字串或假值；未知糖尿病狀態不轉成「無」。分類失敗不影響「已接收」事實，A 不會重送。
- 運算資源忙碌時等待並暫停批次，不終止研究訓練。CUDA 不可用改記為「無法分析」並說明。

### 2.5 介面

- 模型區 `/model-center/clinical-plans`：新增「醫師端預設分析設定」，圖片傳輸與設備擷取分開；只列出相容方案；必填相容依據；顯示不可修改的設定歷史；方案列表顯示模型、類別數、權重摘要與必填欄位。
- 醫師端「真實圖片雙機示範」：①接收位址（自動／手動，進階：連接埠）②目前方案（名稱／封存時間／是否可分析／必填欄位；進階才可改為僅預覽或指定方案）③「開始接收」。項目列表以案例識別顯示真實狀態與缺項。
- 「開啟案例／補充資料」直接開啟該影像所屬案例並捲動到該影像；從後端載入 A 傳來的資料；資料完整時唯讀顯示，不要求再存或再選方案；缺項才展開表單並標示；保存後顯示資料版本與是否已自動排入分析。手動指定方案重新分析移到進階。
- 超音波設備接收：頁面開啟時鎖定一次設備擷取預設方案；檢查已選、方案有效且資料齊全時可按「開始接收與分析」（仍需瀏覽器裝置選擇與相機授權）；缺資料時顯示缺項並只能預覽。最新影格策略、切換時清除舊結果、凍結／保存引用與不自動保存影格均不變。
- A 傳送工具 v2.0.0：每張圖片各自的案例表單（預設空白）；「複製其他欄位到已勾選的圖片」會列出目標並確認，案例識別與側別不被複製；未填案例識別的圖片不能建立批次；顯示 B 方案需要的欄位；連線錯誤分為無法連線、逾時、憑證不符、配對已用或過期、會話結束、版本不相容。

## 4. 兩台電腦的操作

**首次（B，模型區）**：到「模型區 → 醫師分析方案」，在「圖片傳輸」選擇相容的封存方案、填寫相容依據並設定；需要擷取分析時另設「設備擷取」。目前正式資料尚未設定任何預設，接收頁會明確顯示「尚未設定」並拒絕開始，直到設定或明確選擇僅預覽。

**每次使用**：
1. B：醫師工作區 →「真實圖片雙機示範」→ 確認位址與方案 →「開始接收」→ 下載配對檔並核對畫面上的指紋。
2. A：執行 `UltrasoundImageSender.exe` → 匯入配對檔並輸入指紋 → 選擇圖片 → 對每張「填寫案例資料」（可勾選其他圖片後複製共同欄位）→「傳送已選取圖片」。
3. B：自動驗證、建立案例、帶入資料並分析；待補資料的影像按「補充資料」補齊即可。
4. 醫師查看結果，確認內容後建立或編輯報告。

A 的防火牆不需開放；B 需允許接收程序的連接埠（指定埠時尤其要確認）。
